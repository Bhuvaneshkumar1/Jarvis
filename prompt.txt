# 4. CONTRACT DESIGN RULE

Contracts must contain:

* typed fields
* validation
* explicit status
* timestamps where necessary
* IDs where necessary
* serialization support where necessary

Contracts must NOT contain business logic.

Bad:

```python
class Task:
    def execute(self):
        ...
```

Good:

```python
class Task:
    task_id: str
    description: str
    status: TaskStatus
```

Execution belongs to the appropriate runtime/service.

* PIN change

* Authentication sessions
* Session expiration
* Session revocation
* Authentication event auditing
* Brute-force protection foundations

# 3. STRICT SECURITY REQUIREMENTS

The following rules are mandatory.

* Never store the PIN in plaintext.
* Never hardcode a PIN.
* Never store the PIN in `.env`.
* Never print a PIN in logs, terminal output, exceptions, audit events or test reports.
* Never store the PIN in task records, event history or normal application state.
* Never transmit the PIN to an LLM provider or external integration.
* Never allow an unauthenticated user to obtain an authenticated session.
* Never treat a successful module import as proof of authentication.
* Never silently bypass authentication when a security component fails.

The authentication subsystem must fail closed whenever it cannot safely verify credentials.

# 5. PIN POLICY

Implement a configurable PIN policy.

Initial policy:

* Minimum length: 6 digits
* Maximum length: 12 digits
* Numeric digits only
* Leading zeroes must be preserved.
* Empty PINs must be rejected.
* PINs containing whitespace must be rejected.
* PINs containing non-ASCII digits must be rejected unless explicitly supported.
* PIN confirmation must match during enrollment and PIN changes.

Do not silently truncate, normalize or modify PIN input.

Do not convert the PIN to an integer. Preserve it as a string so leading zeroes remain valid.

The policy must be centrally defined rather than duplicated across modules.

# 6. SECURE PIN ENROLLMENT

```text

       |

       |

Enrollment successful
```

Requirements:

1. Enrollment must be an explicit operation.
2. The system must not silently enroll a default PIN.
3. Enrollment must reject invalid PINs.
4. Confirmation must match.
5. The verifier must be derived using a suitable password-hashing algorithm.
6. Persisted data must be verified before reporting success.
7. Re-enrollment must not overwrite an existing credential without an authorized reset procedure.
8. Every enrollment outcome must be auditable without exposing the PIN.

Use a well-maintained password-hashing implementation, preferably Argon2id where supported. Select and document appropriate parameters based on actual measurements on the target hardware.

Do not invent an encryption or hashing algorithm.

The persisted record must never contain the original PIN.

Use a cryptographically secure random salt.

Do not store the credential in an ordinary configuration file.

Prefer the existing secure database or a dedicated protected credential store, depending on the architecture already implemented.

If the current repository lacks a secure persistence layer, implement the smallest compatible persistence mechanism without prematurely building the entire future database subsystem.

Requirements:

* Never reveal whether a particular PIN digit or prefix was correct.

# 4. TASK STATE MACHINE

Implement a centralized, explicit task state machine.

Support the existing lifecycle states and extend them only when necessary.

The state model should cover:

* `CREATED`
* `QUEUED`
* `READY`
* `RUNNING`
* `PAUSED`
* `WAITING_APPROVAL`
* `WAITING_DEPENDENCY`
* `RETRY_PENDING`
* `CANCELLING`
* `CANCELLED`
* `COMPLETED`
* `FAILED`
* `BLOCKED`

Reconcile these names with the existing contracts rather than creating incompatible duplicate statuses.

Define all permitted state transitions explicitly.

Examples:

| Current state      | Event                  | Permitted next state |
| ------------------ | ---------------------- | -------------------- |
| CREATED            | Submit                 | QUEUED               |
| QUEUED             | Dependencies satisfied | READY                |
| READY              | Start                  | RUNNING              |
| RUNNING            | Pause                  | PAUSED               |
| RUNNING            | Approval required      | WAITING_APPROVAL     |
| RUNNING            | Dependency unavailable | WAITING_DEPENDENCY   |
| RUNNING            | Retryable failure      | RETRY_PENDING        |
| RETRY_PENDING      | Retry scheduled        | READY                |
| RUNNING            | Successful completion  | COMPLETED            |
| RUNNING            | Terminal failure       | FAILED               |
| RUNNING            | Cancellation request   | CANCELLING           |
| CANCELLING         | Cancellation confirmed | CANCELLED            |
| WAITING_APPROVAL   | Approval granted       | READY                |
| WAITING_APPROVAL   | Approval rejected      | BLOCKED              |
| WAITING_DEPENDENCY | Dependencies satisfied | READY                |

This table is illustrative. The final state machine must account for all actual states and existing contracts.

Requirements:

* Reject invalid transitions.
* Prevent terminal tasks from being restarted without an explicit, supported retry or new-task operation.
* Do not silently convert `FAILED` into `COMPLETED`.
* Distinguish cancellation requests from confirmed cancellation.
* Do not mark a running task as cancelled while its underlying operation may still be executing.
* Preserve state-transition history.
* Record the reason for every important transition.
* Ensure transitions are atomic.

Do not allow arbitrary callers to update task status by directly modifying database fields.

All state changes must pass through the authoritative task manager.

# 9. OPTIMISTIC CONCURRENCY CONTROL

Implement optimistic concurrency using the task version field or an equivalent mechanism.

Requirements:

* Every successful state mutation increments the version.
* Updates must verify the expected version.
* Concurrent stale updates must be rejected.
* A rejected stale update must not overwrite newer state.
* State transition validation and version verification must occur atomically.
* Conflict errors must be explicit and typed.

For example:

If two components read task version 4 and both attempt to update it, only the first valid transaction should commit. The second must receive a concurrency conflict.

Do not automatically retry stale updates with potentially outdated data.

Test real concurrent database operations.

# 11. RESTART RECOVERY

Implement persistent task recovery integrated with the runtime lifecycle.

On startup, inspect tasks left in nonterminal states.

Identify at least:

* Tasks that were queued.
* Tasks that were ready.
* Tasks that were running when JARVIS stopped.
* Tasks waiting for approval.
* Tasks waiting for dependencies.
* Tasks with pending cancellation.
* Tasks with scheduled retries.

Define a documented recovery policy.

Required behavior:

**Queued and ready tasks**

* Preserve their identity and state.
* Revalidate their dependencies.
* Revalidate their authorization context where applicable.
* Make eligible tasks available for future execution.

**Running tasks**

* Do not assume that they completed.
* Mark interrupted execution as requiring recovery.
* Use an explicit recovery transition supported by the state machine.
* Preserve execution-attempt history.
* Do not blindly execute a non-idempotent task again.

**Waiting for approval**

* Preserve the approval relationship.
* Revalidate the approval when execution is eventually requested.
* Do not automatically approve tasks.

**Waiting for dependencies**

* Reevaluate dependencies.
* Update readiness only through the state machine.

**Cancellation requested**

* Preserve the cancellation request.
* Do not report successful cancellation unless confirmed.

**Scheduled retries**

* Preserve retry state and scheduled time.
* Do not create duplicate retry records after restart.

Recovery must be idempotent. Running recovery repeatedly must not duplicate tasks, attempts or history records.

Do not automatically execute recovered tasks in this batch.

# 6. APPROVAL LIFECYCLE

Implement and enforce a clear approval state machine.

Use the existing Batch 15 state names if they are already defined. Do not introduce incompatible duplicate states.

The lifecycle must support these conceptual states:

* PENDING
* APPROVED
* REJECTED
* EXPIRED
* CANCELLED

Define and validate all permitted transitions.

At minimum:

| Current state | Requested transition | Expected result                        |
| ------------- | -------------------- | -------------------------------------- |
| PENDING       | APPROVED             | Allowed after authorization            |
| PENDING       | REJECTED             | Allowed after authorization            |
| PENDING       | EXPIRED              | Allowed when expiry conditions are met |
| PENDING       | CANCELLED            | Allowed for an authorized cancellation |
| APPROVED      | APPROVED             | Reject duplicate decision              |
| REJECTED      | APPROVED             | Reject invalid transition              |
| EXPIRED       | APPROVED             | Reject invalid transition              |
| CANCELLED     | APPROVED             | Reject invalid transition              |

Terminal states must not be silently reopened.

If a new approval is needed after rejection, cancellation, or expiry, create a new approval request with a new ID.

Do not let callers directly change database status fields without passing through the lifecycle service.

# 8. APPROVAL SCOPE AND ACTION INTEGRITY

Approval must authorize only the operation that was actually reviewed.

An approval must not become a general-purpose permission token.

Preserve the existing Batch 15 scoped approval model.

Enforce the following:

* Approval must be bound to its intended action.
* Approval must be bound to its intended resource or task, where applicable.
* Approval must not authorize unrelated operations.
* Approval must not be reused for a different action.
* Changes to critical action parameters must invalidate the original authorization when they alter the approved operation.
* Expired or cancelled approvals must never authorize execution.
* An approval must not bypass current mandatory security policies.

Implement or reuse a stable request fingerprint mechanism.

The fingerprint must be deterministic for equivalent approved actions.

Exclude non-semantic fields such as display-only timestamps if they do not affect the authorized action.

Do not include credentials or secrets in the fingerprint.

If the action changes after approval, require a new approval whenever the change affects the authorization scope or risk.

Document the exact fields covered by the fingerprint.

# 9. CONCURRENCY AND DUPLICATE DECISIONS

Approval decisions can arrive simultaneously from multiple sources, such as the desktop interface, Telegram, or an autonomous agent.

Implement concurrency-safe decision processing.

Requirements:

* Use transactions and the existing database transaction facilities.
* Use optimistic concurrency or appropriate database-level locking.
* Enforce a single successful terminal decision for each approval.
* Detect stale approval versions.
* Reject duplicate or conflicting decisions.
* Prevent two concurrent requests from both successfully deciding the same approval.
* Ensure a retry cannot create duplicate decision history.
* Ensure database constraints provide an additional integrity boundary.

Test concurrent approval and rejection attempts against the same pending approval.

The outcome must be deterministic: no more than one decision may succeed.

Do not claim concurrency safety based solely on sequential unit tests.

Implement durable approval expiry.

4. Transition eligible pending requests to EXPIRED.
5. Persist expiry transitions.
6. Record the reason and timestamp.
7. Make expiry processing idempotent.
8. Recover pending approvals after restart.

A restart must never turn an expired approval back into a valid pending approval.
