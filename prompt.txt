# 4. CONTRACT DESIGN RULE

Contracts must contain:

* typed fields
* validation
* explicit status
* timestamps where necessary
* IDs where necessary
* serialization support where necessary

Contracts must NOT contain business logic.

Bad:

```python
class Task:
    def execute(self):
        ...
```

Good:

```python
class Task:
    task_id: str
    description: str
    status: TaskStatus
```

Execution belongs to the appropriate runtime/service.

# 25. SERIALIZATION

Contracts must support safe serialization.

```text
object
 ↓
dictionary / JSON
 ↓
object
```

Requirements:

* deterministic field names
* explicit types
* safe handling of optional fields
* timestamps serialized consistently
* enum values serialized consistently

Do not serialize secrets.

# 29. CONTRACT VERSIONING

Design contracts so future fields can be added without breaking existing serialization unnecessarily.

Do NOT build a complex schema-versioning framework yet.

# 30. DEPENDENCY RULE

Contracts must have minimal dependencies.

Do not make:

```text
core/contracts/
```

depend on:

```text
LLM SDKs
Telegram SDK
browser libraries
Windows libraries
OCR libraries
database drivers
```

Contracts belong to the core.

Providers belong to their own subsystems.

---

# 31. CIRCULAR DEPENDENCY RULE

Do not create circular imports.

Required direction:

```text
contracts
    ↓
core services
    ↓
providers/adapters
```

Not:

```text
contracts
 ↔
providers
```

If circular dependency appears, stop and redesign the dependency boundary.

Do not solve architectural problems using arbitrary import hacks.
